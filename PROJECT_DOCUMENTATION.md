# 1. Project Overview

- **Project name:** HomeAssist (`homeassist-backend`, `homeassist-web`).
- **Purpose:** An AI-powered local home-services marketplace for Pakistan that connects customers with verified service professionals (plumbers, electricians, cleaners, AC technicians, carpenters, painters, appliance-repair techs, gardeners).
- **Problem it solves:** Finding a trustworthy, available home-service professional in Pakistan is slow and risky (no verification, no price transparency, no tracking, payment disputes). HomeAssist provides: AI problem-classification → matching to verified pros, transparent PKR pricing, online booking, escrow-protected payments, and live GPS tracking of the provider en route.
- **Target users:**
  1. **Customers** — homeowners/renters in Lahore, Karachi, Islamabad who need a home service.
  2. **Service Providers** — verified tradespeople who list services, set availability, accept bookings, and get paid.
  3. **Admins** — platform operators who verify providers (CNIC check) and monitor stats/revenue.
- **Main features:**
  - AI service classifier + provider recommendations (Groq Llama, keyword fallback).
  - Provider search with filters (category, location, rating, price) and pagination.
  - Two booking flows: **scheduled** (pick a provider + date) and **on-demand dispatch** (auto-match nearest available pro).
  - Full booking lifecycle: pending → accepted/declined → completed → reviewed (+ cancelled).
  - **Escrow payments** (mock JazzCash/Easypaisa/Card) with a 15% platform commission and provider wallet/payout.
  - **Live GPS tracking** with real road routing (OSRM) and ETA.
  - Reviews & ratings with automatic provider average recalculation.
  - Provider dashboard (bookings, wallet, profile, services, availability, live GPS sharing).
  - Admin dashboard (platform stats, escrow/commission overview, provider CNIC verification queue).
  - FAQ support chatbot (Groq) floating on every page.
- **Current development status:** Working full-stack MVP / prototype. Core flows implemented end-to-end. Payments and AI are functional but **mocked/demo-grade** (no real gateway, no real money). Some built code is **not yet wired into routing** (see §16). README and `.env.example` files are stale.

# 2. Business Idea

### Detailed explanation
HomeAssist is a two-sided marketplace ("Uber for home services") localized for Pakistan. Demand side (customers) describes a problem; supply side (providers) is verified, listed, and matched. The platform monetizes by taking a **15% commission** on each paid booking, holding the customer's payment in **escrow** until the job is marked complete, then releasing **85%** to the provider's in-app wallet.

### User workflow

**Customer (scheduled booking):**
1. Land on homepage → search a problem or pick a service category.
2. Browse/filter providers → open a provider profile.
3. Select a service, date/time, address; optionally share a live GPS pin.
4. Confirm booking → pay via the Payment Modal (funds go to escrow / "held").
5. Track provider on a live map once they accept and share GPS.
6. After completion, leave a 1–5 star review.

**Customer (on-demand dispatch — `RequestService` page):**
1. Choose a category, set location (GPS / address search / tap map pin), describe the problem.
2. "Find nearest pro" → backend matches the nearest verified, available provider.
3. A tracking screen polls booking status every 10s; can pay, cancel, or "find another pro" (rematch).

**Provider:**
1. Register as provider with CNIC number + front/back images → awaits admin verification.
2. In dashboard: manage profile, add services (title/price/unit), set weekly availability.
3. Receive booking requests → Accept/Decline → while accepted, browser shares live GPS (watchPosition) so the customer sees the route → Mark Completed.
4. Completion releases escrow → wallet balance grows; can "Withdraw" (mocked).

**Admin:**
1. View platform stats and escrow/commission/payout totals + full transaction table.
2. Review CNIC images in the verification queue → Verify providers (they then go live).

### Real-world use cases
- "My kitchen tap is leaking" → AI classifies as plumbing → recommends top plumbers nearby.
- Emergency same-day need → dispatch nearest available pro and watch them approach in real time.
- A tradesperson wants more jobs → registers, gets verified, receives bookings, builds a 5-star reputation.

### Core value proposition
Trust (CNIC-verified pros), speed (AI matching + on-demand dispatch), safety (live GPS + escrow), and transparency (fixed PKR pricing, ratings).

# 4. Architecture

### High-level architecture
```
┌─────────────────────────┐        /api proxy        ┌──────────────────────────┐
│   React SPA (Vite)       │  ───────────────────────▶ │  Express API (Node)       │
│  - Pages / Components    │   fetch JSON + JWT bearer │  - Routes (auth, providers,│
│  - AuthContext (JWT)     │ ◀─────────────────────── │    bookings, reviews, ai, │
│  - Leaflet maps          │                          │    admin, payments,        │
└─────────┬───────────────┘                          │    dispatch, geo)          │
          │ direct browser calls                      │  - Zod validation          │
          │  • OSRM (route)                           │  - JWT middleware          │
          │  • Carto/OSM tiles                        │  - escrow lib              │
          ▼                                           └───────┬───────────┬───────┘
   3rd-party map/route APIs                       supabase-js │           │ groq-sdk
                                                  rpc(exec_sql)│           │ (LLM)
                                                               ▼           ▼
                                                   ┌────────────────┐  ┌──────────┐
                                                   │ Supabase/Postgres│ │ Groq API │
                                                   │  exec_sql() fn   │ └──────────┘
                                                   └────────────────┘
                                       Backend also proxies → Nominatim (geocoding)
```

### Data flow (request example: create booking)
1. Customer submits booking form (`ProviderDetail.jsx`).
2. `api/bookings.js` → `client.js` `post('/bookings', body)` adds `Authorization: Bearer <token>`.
3. Vite proxies `/api/bookings` → `http://localhost:5000/api/bookings`.
4. Express `bookings.js` route: `authenticate` middleware verifies JWT → `requireRole('customer')` → Zod validates body.
5. Route builds parameterized SQL strings and calls `pool.query(sql, params)` → `lib/db.js` → `supabase.rpc('exec_sql', { sql_text, sql_params })`.
6. The Postgres `exec_sql` function substitutes `$1..$n`, runs the statement, aggregates rows into a JSON array.
7. Rows returned → `deepToCamel()` converts snake_case → camelCase → JSON response.
8. Frontend updates state, shows toast, opens Payment Modal.

### Application flow
- SPA shell: `App.jsx` → `BrowserRouter` → `AuthProvider` → `ToastProvider` → `Navbar` + `FAQChatbot` (global) + routed `<main>` + `Footer`.
- On load, `AuthContext` reads `token` from `localStorage` and calls `/auth/me` to hydrate the user.
- `ProtectedRoute` guards `/bookings` (customer), `/dashboard` (provider), `/admin` (admin).

### Component interaction
- Pages compose **UI primitives** (`Button`, `Input`, `Badge`, `StarRating`, `Skeleton`, `Toast`, `Card`) and **shared components** (`ProviderCard`, `LiveTrackerMap`, `PaymentModal`, `FAQChatbot`, `AIAssistant`, `CategoryGrid`).
- `api/*` modules are thin wrappers over `api/client.js`.

### Design patterns used
- **Layered backend**: routes (controllers) → lib (db/util/escrow) → DB function. No ORM/models layer; SQL is inline in routes.
- **Repository-ish helper**: `BOOKING_FULL_SELECT` / `PROVIDER_FULL_SELECT` reusable SQL templates building nested JSON.
- **Provider/Context pattern** (React) for auth + toasts.
- **Adapter**: `lib/db.js` mimics a `pg` Pool (`query`, `connect`, `release`) so route code reads like node-postgres even though it's Supabase RPC. `BEGIN/COMMIT/ROLLBACK` are **no-ops** (not real transactions).
- **Case-conversion boundary**: DB is snake_case; API/JS is camelCase via `deepToCamel`.

# 8. Backend Analysis

### Services / structure
Express app (`index.js`) with CORS (origin = `CLIENT_URL`), `express.json()`, ten mounted routers, and a final error-handling middleware returning `500 {error:'Internal server error'}`. No controllers/models split — **route files act as controllers**; SQL is inline; `lib/` holds shared helpers.

### Business logic highlights
- **Auth** (`auth.js`): register (hash w/ bcrypt cost 10, create user, create provider row if role=provider), login (compare hash, sign JWT), `/me` (returns user + nested provider, strips `password_hash`).
- **Providers** (`providers.js`): search with dynamic WHERE (location ILIKE, minRating, category EXISTS, maxPrice EXISTS), COUNT for pagination, ORDER BY rating/reviews; full profile via `PROVIDER_FULL_SELECT` (nested user, services, availability, last 10 reviews as JSON); update profile (changing CNIC resets `is_verified=false` for non-admins); add/delete services; replace availability slots; `me/availability` online toggle.
- **Bookings** (`bookings.js`): create (validates provider+service match, refine requires lat&lng together), `mine`/`provider`/`:id` (ownership/role checks), status transitions (only provider can accept/decline/complete; only customer can cancel; admin override) with **escrow side effects** (complete→release, declined/cancelled→refund, wrapped in try/catch so payment errors never block status), and `tracking` (provider pushes lat/lng → computes haversine distance + ETA, only when status=accepted).
- **Dispatch** (`dispatch.js`): `findNearest()` selects verified+available providers offering the category with non-null coords, picks the closest by haversine, cheapest matching service; creates a `pending` booking; `rematch` reassigns to the next-nearest (excluding current), repointing any held escrow.
- **Payments** (`payments.js`): `pay` (validates ownership + unpaid, splits amount, simulated 1.5s delay, inserts `transactions` row status=`held`, sets booking `payment_status='held'`), `release` (provider/admin releases escrow), `wallet` (provider balance + history), `admin/stats` (aggregate revenue/commission/payouts + all transactions).
- **Reviews** (`reviews.js`): only the booking's customer, only when `completed`, unique per booking; inserts review, sets booking `reviewed`, recomputes provider `avg_rating`/`review_count`.
- **Admin** (`admin.js`): unverified queue (with CNIC + services), verify (set `is_verified=true`), platform stats.
- **AI** (`ai.js`): `/chat` FAQ (system-prompted Groq), `/recommend` classify problem → categories/urgency → query matching providers; **keyword fallback** (incl. Urdu words) if no API key or API failure.
- **Geo** (`geo.js`): server-side Nominatim proxy (sets User-Agent, throttles to ≤1 req/sec) for reverse + forward geocoding (country-coded to PK).

### API architecture
- RESTful JSON. Resource-scoped routers under `/api/*`. Consistent error shape `{ error }` (Zod errors returned as an array). camelCase responses via `deepToCamel`.

### Middleware
- `authenticate` — parses `Bearer` token, verifies JWT, sets `req.user` (`{id,email,role,name}`); 401 on missing/invalid.
- `requireRole(...roles)` — 403 unless `req.user.role` is allowed.
- Global error handler in `index.js`.

### Error handling
- Per-route try/catch; Zod errors → 400; not-found → 404; auth → 401/403; conflicts → 409 (duplicate email, already paid, already reviewed); upstream failures → 502 (geocoding). `exec_sql` raises a Postgres exception with `SQLERRM` + truncated query for debugging.

### Security mechanisms (implemented)
- Password hashing (bcrypt), JWT auth, role guards, ownership checks on bookings/providers, Zod input validation, `password_hash` stripped from `/me`, CORS limited to `CLIENT_URL`, Nominatim throttling + identifying User-Agent. (See §17 for gaps.)

# 9. Database Analysis

### Database type
PostgreSQL (Supabase). Defined in `backend/supabase-all.sql`. All runtime access goes through the `exec_sql` SQL function.

### Tables & schema
**`users`** — `id` PK, `role` (default `customer`), `name`, `email` UNIQUE, `password_hash`, `phone`, `location`, `created_at`.

**`providers`** — `id` PK, `user_id` UNIQUE FK→users (cascade), `bio`, `experience_years`, `service_area`, `lat`, `lng`, `is_verified` (default false), `avg_rating` (default 0), `review_count` (default 0), `profile_photo`, `cnic_number`, `cnic_front`, `cnic_back`, `wallet_balance` (default 0), `total_earned` (default 0), `is_available` (default true).

**`service_categories`** — `id` PK, `name` UNIQUE, `icon` (emoji), `slug` UNIQUE. (8 categories: plumbing, electrical, cleaning, ac-repair, painting, carpentry, appliance-repair, gardening.)

**`provider_services`** — `id` PK, `provider_id` FK→providers (cascade), `category_id` FK→service_categories, `title`, `price` (double), `price_unit` (default `fixed`; e.g., per hour/visit/room/piece).

**`availability_slots`** — `id` PK, `provider_id` FK→providers (cascade), `day_of_week` (0=Sun..6=Sat), `start_time`, `end_time` (varchar `HH:MM`).

**`bookings`** — `id` PK, `customer_id` FK→users, `provider_id` FK→providers, `service_id` FK→provider_services, `status` (default `pending`; pending/accepted/declined/completed/reviewed/cancelled), `scheduled_at`, `address`, `customer_lat/lng`, `customer_location_label`, `provider_lat/lng`, `provider_location_updated_at`, `distance_km`, `eta_minutes`, `problem_description`, `payment_status` (default `unpaid`; unpaid/held/released), `created_at`.

**`reviews`** — `id` PK, `booking_id` UNIQUE FK→bookings, `provider_id` FK→providers, `rating` 1–5 CHECK, `comment`, `created_at`.

**`transactions`** — `id` PK, `booking_id` FK, `customer_id` FK, `provider_id` FK, `amount`, `commission`, `provider_payout`, `method` (jazzcash/easypaisa/card), `status` (default `held`; held/released/refunded), `created_at`, `released_at`. Indexes on `provider_id` and `booking_id`.

### Relationships
- user 1—1 provider (a provider IS a user with role=provider).
- provider 1—N provider_services, 1—N availability_slots, 1—N bookings, 1—N reviews, 1—N transactions.
- user(customer) 1—N bookings, 1—N transactions.
- booking 1—1 review, 1—N transactions (effectively 1 held at a time), N—1 service.

### Data flow & important queries
- **`exec_sql(sql_text, sql_params jsonb)`** (SECURITY DEFINER): trims (incl. newlines via `btrim`), no-ops `BEGIN/COMMIT/ROLLBACK`, substitutes `$1..$n` from the JSON params array (strings via `quote_literal`, numbers/bools inline, null→NULL, arrays→`ARRAY[...]`), and for `SELECT/WITH` or anything with `RETURNING` wraps the statement in a CTE and `jsonb_agg`s the rows; otherwise executes and returns `[]`.
- **`BOOKING_FULL_SELECT`** / **`PROVIDER_FULL_SELECT`**: build deeply nested JSON (service+category, provider+user, customer, review / services, availability, reviews) using `jsonb_build_object` and correlated subqueries.
- Review submission recomputes provider aggregates: `SELECT AVG(rating), COUNT(*) … → UPDATE providers`.

> Two access mechanisms exist: **runtime** uses `exec_sql` (Supabase RPC, no real transactions); the **`seed.js`** script uses a direct `pg` Pool with real `BEGIN/COMMIT`. They use different env vars (`SUPABASE_URL`/`SUPABASE_KEY` vs `DATABASE_URL`).

# 10. Authentication & Authorization

- **Login system:** email + password. Server compares bcrypt hash, returns `{ token, user }`. Frontend stores token in `localStorage`, sets user in `AuthContext`, and redirects by role (admin→`/admin`, provider→`/dashboard`, else `/`).
- **Registration:** customer or provider. Providers must supply CNIC number + front/back images and start **unverified** (a provider row is created; admin must verify before they appear meaningfully / pass dispatch's `is_verified` gate).
- **User roles:** `customer`, `provider`, `admin` (admin only seeded, not self-registerable via UI — role enum on register is `customer|provider`).
- **Permissions (enforced server-side):**
  - Bookings: provider-only (accept/decline/complete + tracking), customer-only (create/cancel/review), owner-or-admin reads.
  - Providers: self-or-admin for profile/services/availability edits.
  - Payments: customer pays own booking; provider/admin releases; provider sees own wallet; admin sees platform stats.
  - Route guards client-side via `ProtectedRoute` (UX), authoritative checks server-side (security).
- **Session management:** stateless JWT (7-day expiry), no refresh tokens, no server-side session store, no logout invalidation (client just deletes the token).
- **Security implementation:** see §8 / §17.

# 15. Important Algorithms & Logic

### Nearest-provider matching (dispatch)
`findNearest()` (`routes/dispatch.js`): query verified + available providers offering the category (non-null coords), compute **haversine distance** from the customer to each, pick the minimum; choose that provider's **cheapest** matching service. Rematch excludes the current provider. Distance rounded to 0.1 km.

### Distance & ETA
- **Haversine** (`R=6371km`) in `bookings.js`, `dispatch.js`, and `LiveTrackerMap.jsx`.
- **ETA** = `max(1, round((km / 26) * 60))` minutes (assumes 26 km/h urban speed). When OSRM responds, real route `distance`/`duration` override the estimate.
- **Bearing** (`LiveTrackerMap`) rotates the moving arrow marker toward the customer.

### AI classification
- **Primary:** Groq JSON → `{categories:[slug…], urgency:'low|medium|high|emergency', explanation}`.
- **Fallback `keywordClassify`:** keyword map per category incl. **Urdu** terms (e.g., `pani`, `bijli`, `safai`, `darwaza`, `thanda`, `rang`, `baagh`); defaults to `cleaning` if nothing matches; urgency heuristics (flood/fire/no power → high; routine/whenever → low).

### Escrow / money split (`lib/escrow.js`)
- `COMMISSION_RATE = 0.15`. `splitAmount(amount)` → `commission = round2(amount*0.15)`, `providerPayout = round2(amount - commission)`.
- `releaseEscrow(bookingId)`: held txn → `released` (+ `released_at`), credit provider `wallet_balance` & `total_earned`, booking `payment_status='released'`.
- `refundEscrow(bookingId)`: held txn → `refunded`, booking `payment_status='unpaid'`.

### Search filtering & pagination
- Dynamic parameterized WHERE building (`providers.js`), `COUNT(*)` then `LIMIT/OFFSET`; `pages = ceil(total/limit)`.

### Provider rating recalculation
- On each review: `AVG(rating)`, `COUNT(*)` over provider's reviews → update `providers`.

### Frontend animation logic
- `useReveal` (IntersectionObserver one-shot) + `useCounter` (cubic ease-out via `requestAnimationFrame`) in `Home.jsx`.

### Data shaping
- `deepToCamel` recursively snake→camel; `BOOKING_FULL_SELECT`/`PROVIDER_FULL_SELECT` assemble nested JSON server-side to avoid N+1 client calls.

# 17. Security Review

### Implemented measures
- bcrypt password hashing; JWT auth + role/ownership checks; Zod validation; `password_hash` excluded from responses; CORS restricted to `CLIENT_URL`; Nominatim throttled + identified.

### Potential vulnerabilities / risks
1. **`exec_sql` string interpolation.** The runtime DB layer substitutes params into SQL text inside a `SECURITY DEFINER` function. Strings use `quote_literal` (mitigates classic injection), but this is riskier than true bound parameters and runs with definer privileges — a bug in escaping or a non-string edge case could be dangerous. Treat the Supabase key as highly sensitive.
2. **JWT secret & token storage.** Token in `localStorage` (XSS-exposable). No expiry refresh/rotation/revocation. A weak/committed `JWT_SECRET` would be catastrophic — ensure a strong secret in env only.
3. **Self-service privilege via PUT `/providers/:id`.** A provider can set their own `isVerified=false` indirectly; admin override paths exist — verify no path lets a non-admin set `isVerified=true` (currently only admin route does).
4. **CNIC & profile images as base64 in DB.** Sensitive PII (national ID images) stored unencrypted as text, returned to admin over the API — needs access controls/encryption/object storage in production.
5. **Open AI endpoints.** `/api/ai/chat` and `/recommend` are unauthenticated → potential cost-abuse of the Groq key (no rate limiting).
6. **Mock payments.** No real verification/signature — must not be shipped as real money handling.
7. **No rate limiting / brute-force protection** on login.
8. **Error detail leakage** from `exec_sql` (raises query text on error) — fine for dev, noisy/leaky for prod logs.

### Recommended improvements
- Replace `exec_sql` with real parameterized queries (node-postgres pool) or Supabase client query builders; implement real DB transactions.
- Move tokens to httpOnly cookies; add short expiry + refresh + revocation.
- Add rate limiting (login + AI endpoints), input size limits (base64 uploads), and helmet.
- Store images in Supabase Storage/object store with signed URLs; encrypt PII at rest.
- Add authz tests around booking/provider/payment ownership.
- Integrate a real payment gateway with webhook signature verification before any real launch.

# 18. Performance Review

### Optimizations present
- Server-side JSON assembly (`*_FULL_SELECT`) avoids N+1 round-trips.
- Pagination + `LIMIT` on search; reviews capped at last 10.
- Skeleton loaders; lazy `loading="lazy"` images; font `preconnect`.
- IntersectionObserver one-shot reveals; OSRM fetch cancellation guards in map effect.

### Bottlenecks / concerns
- **`exec_sql` overhead:** each query is an RPC over HTTPS that re-parses/interpolates SQL — higher latency than a pooled connection; no prepared statements; multi-step operations are multiple RPCs.
- **Polling** (`Bookings` 15s, `RequestService` 10s) and continuous `watchPosition` increase load; no websockets.
- **Base64 images** bloat rows and payloads (provider lists/admin queue can be heavy).
- Duplicated haversine/ETA computations; large unused CSS shipped.
- Third-party calls (OSRM/Nominatim) on the request path can be slow/rate-limited.

### Improvement opportunities
- Connection pooling / prepared statements / batched writes; real transactions.
- Replace polling with Supabase Realtime or websockets for tracking/status.
- Object storage for images; CDN; image compression.
- Add DB indexes for common filters (category/slug joins, provider rating/location); purge unused CSS (Tailwind already tree-shakes, but custom blocks remain).
- Memoize/debounce search filter changes; cache categories.

# 20. AI Context Summary

### Complete project summary
HomeAssist is a Pakistan-focused, AI-assisted home-services marketplace (React + Vite SPA / Node + Express API / Supabase Postgres). Customers find or are auto-matched to **CNIC-verified** providers, book services with **transparent PKR pricing**, pay into **mock escrow** (15% platform commission), and watch providers approach via **live GPS tracking** (OSRM routing). Providers manage profile/services/availability, accept jobs, share GPS, and collect wallet payouts. Admins verify providers and monitor revenue. AI (Groq Llama 3.3 70B) powers a FAQ chatbot and a problem-classifier, with a bilingual (English/Urdu) keyword fallback.

### Architecture summary
SPA (`fetch` + JWT in localStorage) → Vite proxy → Express routers (auth, providers, bookings, reviews, categories, ai, admin, payments, dispatch, geo). Express validates with Zod, authorizes via JWT middleware + role/ownership checks, and runs SQL through `lib/db.js` → Supabase `exec_sql` RPC (a custom Postgres function that interpolates params and returns aggregated JSON). DB is snake_case; responses camelCase via `deepToCamel`. Maps/routing/geocoding use OSRM, Nominatim (backend-proxied), and Carto/OSM tiles. No real transactions at runtime; `seed.js` uses a separate direct `pg` pool.

### Important files
- DB access: `backend/src/lib/db.js`; schema/bootstrap: `backend/supabase-all.sql`; money: `backend/src/lib/escrow.js`; SQL JSON templates + case conversion: `backend/src/lib/utils.js`.
- Routing/guards: `frontend/src/App.jsx`; HTTP+auth: `frontend/src/api/client.js`; auth state: `frontend/src/contexts/AuthContext.jsx`.
- Heaviest logic: `pages/ProviderDashboard.jsx` (5 tabs, GPS sharing), `pages/RequestService.jsx` (dispatch, *unrouted*), `components/shared/LiveTrackerMap.jsx` (OSRM routing).

### Important business rules
- Commission **15%**; provider payout **85%**; funds **held** on pay, **released** on completion, **refunded** on decline/cancel.
- Booking lifecycle: `pending → accepted|declined`, `accepted → completed → reviewed`, customer may `cancel` while pending/accepted.
- Only the **provider** accepts/declines/completes & pushes tracking; only the **customer** creates/cancels/reviews; **admin** can override and verify.
- Reviews only on **completed** bookings, **one per booking**; provider average auto-recalculates.
- Providers start **unverified**; CNIC (number + front/back images) required; changing CNIC **resets verification**; dispatch only matches **verified + available + geo-located** providers.
- Cities: Lahore, Karachi, Islamabad. 8 categories (plumbing, electrical, cleaning, ac-repair, painting, carpentry, appliance-repair, gardening). Currency PKR.

### Coding conventions
- Backend: CommonJS, Express routers as controllers, inline parameterized SQL via `pool.query(sql, params)`, Zod validation, `try/catch` with `{error}` responses, `deepToCamel` on output, snake_case DB / camelCase JS.
- Frontend: React function components + hooks; `api/*` wrappers over `client.js`; Context for auth/toast; Tailwind utility classes (variant maps in primitives); status→style dictionaries; toasts for outcomes; skeletons for loading.
- Naming: design tokens prefixed `ha-`; provider code format `HA-PROV-0000`.

### Design conventions
- Light, warm theme (cream `#F8F5F1`, green primary `#16A34A`, amber accent, teal for verified/escrow). Fonts: Outfit (display), Plus Jakarta Sans (body), JetBrains Mono (numbers). Rounded cards + soft shadows; subtle scroll-reveal/orb/particle motion. A dark/glassmorphism utility set exists but is largely unused.
